# Win16 runtime spike: Rust for a 16-bit code segment

Question: can the `win16` renderer and runtime be 16-bit (no Win32s) and written in Rust, with Open Watcom C as the fallback? The code is in [`retro/win16/`](../retro/win16/).

## Verdict

**Works, with limits.** Rust `no_std` built for LLVM's `code16` mode, linked by `rust-lld` and rewrapped by our own packer into a Win16 NE executable, runs on real Windows for Workgroups 3.11 in 386 Enhanced mode, on Windows ME and on Wine. A 14.9 KB `SETUP.EXE` shows a native wizard dialog and a progress dialog, copies a bundled file to `C:\LIMTEST\HELLO.TXT` byte for byte, writes an INI receipt and logs its result.

The limits that matter: the code needs a 386 or later (operand-size and address-size prefixes), so Windows 3.1 Standard mode on a real 286 is out; Windows does not keep the high halves of the 32-bit registers (or even BX), so every API call goes through a stub that saves and restores them; and the toolchain is an unsupported use of LLVM, held together by our packer and a pinned compiler. None of that blocked the spike, but the first two are structural.

## Stage 1: toolchain

`rust-toolchain.toml` pins 1.98.0. The build uses `RUSTC_BOOTSTRAP=1 cargo build --release` with `build-std = ["core", "alloc"]` and `compiler-builtins-mem` (`.cargo/config.toml`). The crate has its own `[workspace]`, so the main workspace never builds it and `cargo fmt --all -- --check` stays green.

The target's `llvm-target` is `i386-unknown-none-code16`, the same mode the rust-osdev real-mode stages use. Rust 1.98 accepted the stock i386 data layout and warned only that soft float is being phased out.

The linker is the hard part. Code and data both start at offset 0 of their own segment, which lld refuses (`virtual address range overlaps`). An `OVERLAY 0 : AT(0x1000)` block with `.text` and `.data` inside it links; `.bss` is folded into `.data`, and `.rodata` lives in the data segment because code reaches strings through DS. The first 16 bytes of the data segment are reserved (`.data.00_reserved`) because Windows writes its local-heap and stack bookkeeping there; without it the first string in the program was overwritten ("Hello P omÅ" on screen).

Disassembly of `msgbox` (`objdump -d -M i8086,intel`) shows 16-bit mode with 32-bit operations through prefixes:

```text
  ab:	66 6a 00             	pushd  0x0
  bd:	66 e8 91 ff ff ff    	calld  54 <MessageBox>
  c3:	66 83 c4 10          	add    esp,0x10
  ca:	66 c3                	retd
  d2:	67 66 8b 74 24 14    	mov    esi,DWORD PTR [esp+0x14]
```

`66` is the operand-size prefix and `67` the address-size prefix. Calls are 32-bit near calls (four bytes of return address), and the stack is addressed through ESP, so the high half of ESP must be zero whenever Rust code runs.

## Stage 2: NE packer

`ne_pack.py` reads the ELF section headers and symbol table and writes: the MZ stub ("This program requires Microsoft Windows."), the NE header (flags `0x0302`, auto-data segment 2, `SS:SP = 2:0`, stack 8 KB, heap 4 KB), a fixed preloaded code segment and a data segment, one relocation record per import (far address, imported ordinal), optional selector fixups, the entry table for exported procedures, resident and non-resident names, the module-reference and imported-names tables for KERNEL, USER and GDI, and a resource table with dialogs, strings and raw data.

- **Import stubs.** `gen_imports.py` reads `tools/imports.tbl` (ordinal and an argument string such as `wppw`) and writes Pascal-convention stubs: arguments pushed left to right as words, longs high word first, near pointers as `DS:offset`, the far call with an operand label `__w16imp_<MODULE>_<ordinal>_<Name>` that the packer turns into a fixup, then DX:AX folded into EAX. `--check-spec DIR` checks every ordinal and argument count against Wine's `.spec` files (fetched with `curl` from `gitlab.winehq.org`); all 64 entries pass.
- **Entry and exports.** `_start` calls INITTASK first, then WaitEvent(0) and InitApp(hInstance), runs `w16_main` and exits through INT 21h/4Ch. `export_proc!` builds an exported far procedure that loads DS and ES from SS (a callback runs on the task's stack, so this needs neither `MakeProcInstance` nor a fixup), saves the registers, clears the high half of ESP and passes the four words as 32-bit arguments. Selector fixups (`__w16sel_code_*`, `__w16sel_data_*`) are implemented and tested but unused.
- **Validation.** `ne_dump.py` is a separate parser. Header and segment fields match Open Watcom's `wlink` output for a message box (flags, auto-data, SS:SP, segment flags, fixup type). The tests build a synthetic ELF and check header fields, relocation bytes, entry table, names, resources and the size limits.

## Stage 3: hello

`msgbox` is one `MessageBox`. `hello` shows a message box, registers a class, creates a window, paints with `TextOut`, runs `GetMessage`/`TranslateMessage`/`DispatchMessage`, and opens the `DIALOG` resource (id 100) from `WM_CREATE`. The dialog procedure is a three-page state machine in `src/wizard.rs`: `step(state, button)` returns `Show`, `Finish` or `Cancel`; page text and the Next/Install/Finish label come from the string table. Cancel ends the dialog, and closing the dialog destroys the window and ends the loop. It runs on all three environments; the 3.11 run was driven to page 1 and the SETUP run (same wizard code) through all three pages.

## Stage 4: installer proof

`SETUP.EXE` (14,944 bytes) does this:

1. Wizard (welcome, install, finish), a native dialog resource.
2. A modeless progress dialog (`CreateDialog`) with a text bar and percentage, updated per 128-byte chunk while a `PeekMessage`/`IsDialogMessage`/`Yield` loop runs, with Cancel honoured.
3. `FindResource`, `LoadResource` and `LockResource` for the bundled `HELLO.TXT` (RT_RCDATA 1), `mkdir` by INT 21h/39h, then `_lcreat`/`_lwrite` of the far resource data to `C:\LIMTEST\HELLO.TXT`.
4. Reads the file back with `_lopen`/`_lread` and compares checksums.
5. `WritePrivateProfileString` for `C:\LIMTEST\INSTALL.INI` and `GetPrivateProfileString` to check it.
6. Writes the log to `C:\LIMTEST\RESULT.LOG`, `D:\RESULT.TXT` and `A:\RESULT.TXT` (the harnesses read whichever exists; `SetErrorMode(1)` stops missing drives asking questions).

On Windows 3.11 and ME the log ends `checksum: source D5966D2E, copy D5966D2E`, `ini: ... match`, `RESULT: PASS`, and `cmp` shows the copy identical to `res/payload/HELLO.TXT`.

Not done: the Program Manager group. Creating one needs a DDE conversation with `PROGMAN` (`[CreateGroup]`, `[AddItem]`); there is no stub for it and it was not attempted. No icon resource was packed. Uninstall, the receipt format (`INSTALL.LIR`) and the Lua subset are outside the spike.

## Stage 5: risk tests

**(a) High register halves.** `probe.rs` fills EBX, ESI, EDI and EBP with patterns whose high halves are non-zero, makes one raw API call and logs what came back. Windows 3.11, 386 Enhanced, before and after the dialogs:

| Call | EBX | ESI, EDI, EBP | ESP |
|---|---|---|---|
| `GetVersion` | kept | kept | kept |
| `GlobalAlloc` | replaced (`0000121E`) | kept | kept |
| `PeekMessage` | replaced (`00000000`, later `111104D3`) | kept | high half became `8001` |
| `Yield` | kept, then high half zeroed after the dialogs | kept | high half `8001` after the dialogs |

Windows ME: `GlobalAlloc` and `PeekMessage` replace EBX, and ESP's high half became `EA06` after `PeekMessage`; `Yield` and `GetVersion` kept everything. Wine kept everything.

So **BX is not preserved even in its low half** (a Pascal callee only owes SI, DI, BP and DS), the high half of ESP can come back non-zero, and a yielding call can change a register an earlier call left alone. ESI, EDI and EBP survived every sample, but nothing promises that. The runtime therefore saves EBX, ESI and EDI in every stub and in `export_proc!`, clears the high half of ESP after every call, and reloads ES from DS (Windows does not keep ES, and Rust's `rep movs` uses it). With those, `SETUP` passes; without the ES reload it died with a General Protection Fault at `0001:07B5`, a `rep movsb` in `save_log`.

**(b) Sizes against the 64 KB limits.**

| Program | File | Code (limit 64 KB) | Data (limit 64 KB, with 8 KB stack and 4 KB heap added) |
|---|---|---|---|
| `msgbox` | 620 B | 261 B | 44 B |
| `hello` | 3,440 B | 1,986 B | 464 B |
| `setup` | 14,944 B | 6,258 B | 4,624 B |

`setup` uses about 10% of the code segment and 28% of the data segment (with the stack and heap counted). The packer rejects a code segment over 64 KB or data plus stack plus heap over 64 KB; it does not split code across segments.

**(c) Standard mode.** The expected result is that Windows 3.1 Standard mode on a 286 fails: every Rust function is full of `66`/`67` prefixes and 32-bit registers, which a 286 treats as invalid opcodes. This could not be shown. The WfW 3.11 tree refuses to start in Standard mode, and no 286 Windows 3.1 install was set up (the retail floppy images exist but were not installed). On a 386 or later running Standard mode the CPU would execute the prefixes, so the real floor is "a 386 or later", which is D4's DOS floor too.

## Limits

| Area | Limit or finding |
|---|---|
| CPU | 386 or later; Windows 3.1 Standard mode on a 286 is unsupported (untested, expected to fail) |
| Code size | One code segment, 64 KB; the packer has no multi-segment support |
| Data, stack, heap | One data segment (DS = SS), 64 KB for data, 8 KB stack and 4 KB heap; no `alloc` allocator was written (the `alloc` crate builds but is unused) |
| Registers | Windows clobbers BX and the high half of ESP; stubs and wrappers save EBX, ESI, EDI and rebuild ESP and ES |
| Pointers | 32-bit values whose high half must stay zero; far pointers (resources, API arguments) are built by hand as `selector:offset` |
| Formatting | No `core::fmt` (the log builder does decimal and hex by hand) |
| Tooling | `RUSTC_BOOTSTRAP=1`, `-Zbuild-std`, a custom target, an `OVERLAY` linker script and our own packer; `code16` is meant for bootloaders |
| Startup | `INITTASK` must be the first instruction executed; anything before it breaks it |
| Fixups | Non-additive fixups are chains; each site must hold 0xFFFF |
| Resources | Lengths are rounded to the alignment, so raw data carries a 4-byte length prefix |
| Installer | Copies files, writes INI, shows native dialogs; cannot create Program Manager groups (DDE not done); no icons |

## Comparison with Open Watcom

`reference.sh` builds the same message box in the `retro/` image (Open Watcom v2, `wcl -bt=windows`).

| | Rust (`msgbox`) | Open Watcom (`hello.c`) |
|---|---|---|
| File size | 620 bytes | 1,478 bytes (1,250 with `-os -s`) |
| Code, data | 261 B, 44 B | 862 B, 290 B |
| CPU | 386 | 286 (16-bit code, no prefixes) |
| Toolchain | pinned Rust, `-Zbuild-std`, custom target, linker script, our packer | one container, `wcl` |
| Resources | our JSON and packer | `wrc` (not tried) |
| Packer to maintain | yes (about 400 lines of Python, tested) | no |

The Rust build is smaller because Open Watcom's C runtime startup and stack-check code is in every executable. An Open Watcom `SETUP.EXE` equivalent to the Rust one was not built, so there is no like-for-like size or effort figure for the full installer. The honest effort comparison is that the Rust path cost the packer, the stub generator and six real-Windows bugs found one at a time by boot-and-look, while the C path would start from a tool that already writes NE files.

## What failed on the way

Each of these worked on Wine or looked right on paper and failed on real Windows 3.11:

1. **"Insufficient memory to run this application."** Non-additive fixups are chained: Windows reads the next fixup's offset from the site it is about to patch, and 0xFFFF ends the chain. The linker left zeros, so the loader walked into offset 0. Fixed in the packer.
2. **Message box text corrupted.** Windows writes into the first 16 bytes of the auto-data segment. Fixed with a reserved block.
3. **Task died inside INITTASK.** Instructions before the INITTASK call (a `movzx esp, sp`) changed what INITTASK saw.
4. **Dialog never opened.** Resource lengths are in alignment units, so the file was too short. Fixed by padding, which also meant raw data needs a length prefix.
5. **General Protection Fault in `rep movsb`.** Windows does not keep ES. Stubs now reload it.
6. **`_lcreat` failed after a `mkdir`.** INT 21h clobbers registers the compiler thought were safe; the inline assembly now saves EBX, ESI and EDI.

## Not done or not verified

- Windows 3.1 Standard mode and a real 286 (expected to fail), Windows 3.0, and real hardware.
- Program Manager group creation (DDE), icons, uninstall and the Lua subset.
- An Open Watcom installer built for comparison.
- Multi-instance behaviour: `export_proc!` takes DS from SS, which is right for the task's own stack; it was not tested with two instances.
- An allocator for `alloc`, and code in more than one segment.
- Mouse-driven clicking on the DOSBox-X harness was unreliable; everything there was driven by keyboard. The first Windows ME boot froze twice with host audio active; with the VM's audio driver set to `none` for the session the run was clean. The VM was restored to the `before win16 spike` snapshot afterwards, and that snapshot is still in the VM's snapshot list.

## Recommendation

Keep Rust as the `win16` runtime's direction, but treat it as a bet with a fallback, not a decision to ship on. The evidence says it loads and runs on the real thing, produces a program a third the size of the C equivalent, and lets the retro runtime share code and tooling with the rest of the project. Against that: the target is a 386-only subset of "Windows 3.x", the toolchain depends on an unsupported LLVM mode behind an unstable `-Z` flag, and every register convention had to be discovered on a running system.

- Take Rust forward if the Windows 3.x audience is 386 and later (the floor D4 already sets for DOS). Next steps: an allocator over `LocalAlloc`, the DDE group call, multi-segment code, an icon resource and a second Windows 3.1 retail install for Standard-mode and clean-install runs.
- Fall back to Open Watcom C if Standard mode on a 286 matters, or if the pinned-nightly-feature risk becomes a maintenance cost the project does not want. The `retro/` image already builds Win16 programs, and the DOS runtime uses it anyway.

The decision is recorded as D46 in [decisions.md](decisions.md).

## Reproducing

```bash
# Build (output outside the tree; delete it afterwards)
CARGO_TARGET_DIR=/tmp/win16-target OUT_DIR=/tmp/win16/out bash retro/win16/build.sh

# Packer and generator tests
python3 -m unittest discover -s retro/win16/tests -v

# Check the import table against Wine's ordinals
curl -o /tmp/win16/krnl.spec https://gitlab.winehq.org/wine/wine/-/raw/master/dlls/krnl386.exe16/krnl386.exe16.spec
python3 retro/win16/tools/gen_imports.py --check-spec /tmp/win16 retro/win16/tools/imports.tbl /tmp/win16/imports.rs

# Open Watcom reference (needs the retro image)
bash retro/win16/reference.sh
```

The Windows 3.11 harness mounted the extracted tree as `C:` and a scratch directory as `D:` in DOSBox-X (`machine=svga_s3`, `cputype=pentium`, `ems=false`, `win /3`), set `run=D:\SETUP.EXE` in `WIN.INI`, removed the Startup group from `PROGMAN.INI`, and sent Return with `xdotool` under Xvfb. Windows ME used a floppy image made with `mformat` and `mcopy`, Windows+R and `keyboardputstring`, and the result was read back with `mcopy` after power off.
