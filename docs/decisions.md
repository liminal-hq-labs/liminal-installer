# Decisions

Each decision is numbered and stays here even when superseded, with a note on what replaced it. Open questions move here once they are answered.

| # | Decision | Choice | Why |
|---|---|---|---|
| D1 | Home | A Liminal HQ Labs experiment in `liminal-hq-labs/liminal-installer`, public from the first commit | Try the idea in the open before it earns a place in Liminal HQ |
| D2 | Licence | `Apache-2.0 OR MIT` | House licence, compatible with both ecosystems |
| D3 | Dependency updates | No Dependabot configuration until the project opts in | Labs repositories stay quiet by default. See the [Labs charter](https://github.com/liminal-hq-labs/.github/blob/main/docs/labs-charter.md#dependabot-is-opt-in) |
| D4 | DOS floor | A 386 or later with a DOS extender | Keeps the retro runtime small enough for a floppy without the cost of real-mode 8086 support |
| D5 | `canvas` controls | The renderer draws its own controls, with native accessibility hooks added later; only the scaffold exists now | One look on every platform from a small binary, without waiting on per-toolkit controls |
| D6 | Hub feeds | The Hub reads multiple feeds, each with its own pinned key | A publisher's key only ever vouches for that publisher's feed |
| D7 | Delta updates | Deferred | Whole-file updates are enough to ship the first version, and the receipt format leaves room for chunks later |
| D8 | Theme sharing | Themes are shared through a theme section in any feed | Reuses the signing and pinning that feeds already have, with no separate gallery to run |
| D9 | Final name | The working name stays `liminst` until one is chosen from the Names board | The name and CLI command change together, once, rather than twice |
| D10 | Release automation | A tag-triggered `release.yml` builds `liminst` and the engine runner natively on each platform's runner, packages the examples with each platform's own tools, and publishes a GitHub release with `SHA256SUMS`. Signing and notarisation steps run only when their secrets exist | Native runners avoid cross-compiling the platform tools (WiX, `productbuild`, `makeappx`). Optional secrets keep forks and early tags working. FreeBSD is best effort because its runner is a virtual machine |
| D11 | The runner | A small separate binary, `liminal-engine`, carried in the `.run` next to the `.lip`, and kept in `{install}/.liminal/runner/` afterwards | The CLI stays a build tool, the stub stays plain shell, and update, repair and uninstall need nothing that was not installed |
| D12 | Project in the payload | A built `.lip` bundles the project under `_project/`; an update's `.lip` brings its own project, but the feed key stays the one pinned at install | The runner walks the real flows, layouts and scripts from one verified file, a release may change them, and a feed cannot swap the key that vouches for it |
| D13 | Signatures | Detached Ed25519 over exact bytes, as hex, in `<file>.sig`; keys are one line of hex; `liminst keygen` makes them | One simple scheme for feeds and themes that shell tools and other languages can check without a container format |
| D14 | No terminal | The runner falls back to headless answers when stdin or stdout is not a terminal; URLs are fetched with `curl` | A `.run` works over SSH, in CI and in containers without extra flags, and the runner avoids bundling an HTTP and TLS stack until it needs one |
| D15 | Studio chrome | The desktop window draws the shared Liminal HQ chrome (`@liminal-hq/waypoint-chrome`), vendored as a copy in `apps/studio/ui/vendor/studio-chrome` with `--wp-`/`data-wp-` renamed to `--lic-`/`data-lic-`; a browser tab keeps the page's own header. The Studio's design tokens come from the design system export in `src/styles/tokens.json` through `bun run tokens`, and every `--lic-*` token the chrome reads is mapped to them | The chrome ships as source with no build step, and Waypoint, Planboard and Fizz Level Studio already use it, so one title bar, menu and dialog behaviour. A copy rather than a cross-repo path keeps the Studio building on its own, as Planboard does. `vendor/studio-chrome/PROVENANCE.md` records the source commit, the changes and the refresh steps. The package is React, so the chrome is a React island around the vanilla screens |
| D16 | Menus | Every command is declared once in `src/chrome/menuModel.ts`. The app menu is one flat list of groups separated by single lines, with no submenus, and the menu bar (File, Edit, View, Project, Help) is built from the same groups, so labels, shortcuts, ticks and enabled state cannot drift. The menu bar is a checkbox in the app menu and in the bar's View menu; with it on, the bar carries F10, Alt and the mnemonics and the wordmark opens nothing | Mirrors Planboard and Fizz Level Studio. One model also means the shortcut handler uses the same table as the menus |
| D17 | Dialogs and settings | About, Preferences and confirmations are Tauri child windows of the main window (the same page loaded with `?window=<kind>`, under the chrome's title bar with only Close), created by the `open_window` command, centred on the parent and modal for About and confirmations. `src/chrome/dialogWindow.ts` opens one, waits for its answer and closes it, with an in-page fallback for the browser demo only. Preferences is the shared settings shell. The `menuBar` and `theme` settings live in `settings.json` in the app's config directory, read and written by `read_settings` and `write_settings`, and every window hears changes by the `studio://settings-changed` event. The context menu stays in-page | Child windows work better than overlays on a desktop: they can leave the main window, take the platform's modality and follow the window manager. The open-project picker is already the platform's own dialog. A settings file is shared by every window and survives a cleared webview, which browser storage does not |
| D18 | Driving the Studio in dev | `bun run tauri:dev` runs the shell with `tauri.conf.dev.json` (`withGlobalTauri`), and debug builds off Windows register `tauri-plugin-mcp-bridge` with a `dev-automation` capability that names every window, so the Tauri MCP server can drive the running app. A UI test fails if the release config enables the global Tauri, if the bridge is not gated on `debug_assertions` and `not(windows)`, or if a child window is missing from the capability | An agent and a person can screenshot and click the real window, including its child windows, the same way as in Planboard. Gating at compile time, in the dependency table and in a test keeps it from reaching a release build |
| D19 | Studio engine backend | `EngineBackend` in `li-studio` implements `StudioBackend` over `li-engine`, `li-script` and `li-render-tui` and is what the desktop shell runs; `MockBackend` stays for tests and the browser demo. A preview walks the install flow with `cond::eval_bool` so `when` and branches decide which steps and screens appear, and draws each screen with the `tui` renderer as an SVG text dump. A script test loads the source in the sandbox and runs its hooks against a sample page and plan, so a denied capability is a failed test. `check` is the Studio's checks plus the engine's, not the CLI's `DefaultChecker` | The Studio shows what an install does, not an approximation. Reusing the engine's conditions and scripts means a preview and a real run cannot disagree. The CLI's checker lives in a crate that pulls in packaging, so the Studio keeps its own equivalent checks and adds the engine's |
| D20 | Project layouts, built-in actions and targets | Layouts resolve from the target's theme, then its `fallback` chain in the project, then the shared `installer/layouts/`; `fallback = "plain"` names the built-in look. A step's `on_enter` may be `builtin:check-feed` or `builtin:launch-app`. A target is unique by `os-arch:renderer`, so one platform may ship a `canvas` and a `tui` target | The examples and the Studio keep layouts in one shared folder, which avoids copying every layout into every theme, and the engine now agrees with them. Built-ins are carried out by the lifecycle, so the flow runner skips them. Two renderers on one platform are two targets, not a duplicate |
| D21 | Studio preferences | Preferences is a child window with the shared `SettingsShell` (seven sections: General, Appearance, Editor, Preview, Agents, Projects, Advanced). Every change applies at once and is written to `settings.json` as a merge; a refused write restores the value and says why on its row. The file carries a `version`, is validated field by field in Rust and TypeScript, migrates the two-key file, keeps keys it does not know and holds no secret. `tauri-plugin-window-state` remembers the size of the main and Preferences windows; `tauri-plugin-system-appearance` supplies the colour scheme and reduced-motion setting for Follow system. The agent server starts, stops and moves with its settings, its token is shown only on request and replaced from Preferences, and no log line carries it. Open recent is the one submenu in the otherwise flat app menu | A window like the other Liminal HQ apps' keeps every preference in one place and applies it for real. A merge keeps settings from different windows from overwriting each other, and unknown keys survive a downgrade. A token printed at start ends up in logs, and one that cannot be replaced cannot be revoked. A list of up to 20 recent projects does not fit as flat rows, which is the case D16 allows a submenu for |
| D22 | JavaScript tooling | Bun runs the Studio's JavaScript: a root `package.json` with `workspaces`, `packageManager` set to `bun@1.4.4`, one `bun.lock`, `.node-version` for Node 24, and `bun run` in the Tauri `beforeDevCommand` and `beforeBuildCommand`. CI uses `oven-sh/setup-bun`. | The Liminal HQ house patterns choose Bun for new apps; pnpm was a default, not a decision |
| D23 | Rich previews | `run_preview` returns each step's resolved layout tree, page state and sample values, and the Studio draws them as the target's look (DOS text, Windows 95 classic, Afterglow or Neutral) from one HTML renderer that the Layouts screen shares; the `tui` text dump is a collapsible extra for `tui` targets. A theme keeps its own install-flow layouts in `themes/<id>/layouts/`, and `layouts/` holds the plain fallback. Neutral gains a generic `installshield-classic` theme. VT323 is bundled from `@fontsource/vt323` | A text dump does not show what a person sees, and the examples should look like the designs. One renderer for both screens means a layout edit and a dry run cannot disagree. Per-theme layouts stop the DOS and Windows looks sharing one tree with overrides, which the designs differ too much for |
| D24 | Project folder names | The engine loads a project from the folder that holds `installer.toml` (`Project::load_installer_dir`), whatever it is called; `Project::load` still takes the folder that holds `installer/`. The Studio uses the former | The Studio already opened any folder with an `installer.toml`, so check and preview must not refuse the same folder |
| D25 | Headless MCP | `liminst studio --mcp [--port N]` opens the `-C` project over `EngineBackend` and serves `McpServer` on `127.0.0.1` until Ctrl+C. Standard output starts with `Studio MCP server: <url>` and `Token: <token>`, a new token each run, printed once. History is in memory and writes go to disk | CI and remote shells can have an agent edit a project without a window, and the one stdout format lets a script read the address and token. A token in stdout is the only way a headless run can hand it over |
| D26 | GraphQL | Deferred. The Studio's agent API is MCP only | MCP covers what an agent needs, and a second API would double the surface to keep in step before anything uses it. The decision is revisited when a client needs queries MCP tools cannot answer |
| D27 | More Studio windows and menu items | New project (`Ctrl+N`), Keyboard shortcuts (`Ctrl+/`) and Connect an agent are child windows, from the File and Help menus. `liminst init`'s scaffold moves into `li_studio::scaffold` so the Studio and the CLI write the same files. A failed agent server start is kept by the shell and shown on the agent card and in Preferences. Opening a different project resets the per-project state of the app. Build all and the Feeds and Builds screens wait for a later change | The design lists these items, and a form that writes the files itself would drift from `liminst init`. A start failure that only reaches stderr is invisible in a desktop app. Stale ids and selections from another project made the new one load nothing |
| D28 | Script editor | The Scripts screen is CodeMirror 6 mounted by hand and kept alive across redraws, with the packages pinned to the versions Fizz Level Studio uses. The text lives in `scriptDraft` in app state, and `scriptDirty` is derived from it. Syntax errors come from `check_script_syntax`, which compiles the source in an empty Lua state without running it, and the warnings (undeclared capabilities, removed globals, hook parameters, what the retro subset lacks) come from the same call. `test_script` takes a target and builds its sample from it | Unsaved text in a textarea was lost by any redraw and invisible to File > Save. Running a script's top level to find errors would execute it, and a real parser cannot be written twice in the UI. A test that ignores the target cannot show how a script varies across targets. The retro subset list is the one assumption: `li.net`, `utf8`, `string.pack`, `string.unpack`, `string.packsize`, `goto` and `<close>` |
