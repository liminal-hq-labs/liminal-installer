# Decisions

Each decision is numbered and stays here even when superseded, with a note on what replaced it. Open questions move here once they are answered.

| # | Decision | Choice | Why |
|---|---|---|---|
| D1 | Home | A Liminal HQ Labs experiment in `liminal-hq-labs/liminal-installer`, public from the first commit | Try the idea in the open before it earns a place in Liminal HQ |
| D2 | Licence | `Apache-2.0 OR MIT` | House licence, compatible with both ecosystems |
| D3 | Dependency updates | No Dependabot configuration until the project opts in | Labs repositories stay quiet by default. See the [Labs charter](https://github.com/liminal-hq-labs/.github/blob/main/docs/labs-charter.md#dependabot-is-opt-in) |
| D4 | DOS floor | A 386 or later with a DOS extender | Keeps the retro runtime small enough for a floppy without the cost of real-mode 8086 support |
| D5 | `canvas` controls | The renderer draws its own controls, with native accessibility hooks added later; only the scaffold exists now | One look on every platform from a small binary, without waiting on per-toolkit controls |
| D6 | Hub feeds | The Hub reads multiple feeds, each with its own pinned key | A publisher's key only ever vouches for that publisher's feed |
| D7 | Delta updates | Deferred | Whole-file updates are enough to ship the first version, and the receipt format leaves room for chunks later |
| D8 | Theme sharing | Themes are shared through a theme section in any feed | Reuses the signing and pinning that feeds already have, with no separate gallery to run |
| D9 | Final name | The working name stays `liminst` until one is chosen from the Names board | The name and CLI command change together, once, rather than twice |
| D10 | Release automation | A tag-triggered `release.yml` builds `liminst` and the engine runner natively on each platform's runner, packages the examples with each platform's own tools, and publishes a GitHub release with `SHA256SUMS`. Signing and notarisation steps run only when their secrets exist | Native runners avoid cross-compiling the platform tools (WiX, `productbuild`, `makeappx`). Optional secrets keep forks and early tags working. FreeBSD is best effort because its runner is a virtual machine |
| D11 | The runner | A small separate binary, `liminal-engine`, carried in the `.run` next to the `.lip`, and kept in `{install}/.liminal/runner/` afterwards | The CLI stays a build tool, the stub stays plain shell, and update, repair and uninstall need nothing that was not installed |
| D12 | Project in the payload | A built `.lip` bundles the project under `_project/`; an update's `.lip` brings its own project, but the feed key stays the one pinned at install | The runner walks the real flows, layouts and scripts from one verified file, a release may change them, and a feed cannot swap the key that vouches for it |
| D13 | Signatures | Detached Ed25519 over exact bytes, as hex, in `<file>.sig`; keys are one line of hex; `liminst keygen` makes them | One simple scheme for feeds and themes that shell tools and other languages can check without a container format |
| D14 | No terminal | The runner falls back to headless answers when stdin or stdout is not a terminal; URLs are fetched with `curl` | A `.run` works over SSH, in CI and in containers without extra flags, and the runner avoids bundling an HTTP and TLS stack until it needs one |
| D15 | Studio chrome | The desktop window draws the shared Liminal HQ chrome (`@liminal-hq/waypoint-chrome`), vendored as a copy in `packages/chrome` with `--wp-`/`data-wp-` renamed to `--lic-`/`data-lic-`; a browser tab keeps the page's own header. The Studio's design tokens come from the design system export in `src/styles/tokens.json` through `bun run tokens`, and every `--lic-*` token the chrome reads is mapped to them | The chrome ships as source with no build step, and Waypoint, Planboard and Fizz Level Studio already use it, so one title bar, menu and dialog behaviour. A copy rather than a cross-repo path keeps the Studio building on its own, as Planboard does. `vendor/studio-chrome/PROVENANCE.md` records the source commit, the changes and the refresh steps. The package is React, and since D34 so are the screens |
| D16 | Menus | Every command is declared once in `src/chrome/menuModel.ts`. The app menu is one flat list of groups separated by single lines, with no submenus, and the menu bar (File, Edit, View, Project, Help) is built from the same groups, so labels, shortcuts, ticks and enabled state cannot drift. The menu bar is a checkbox in the app menu and in the bar's View menu; with it on, the bar carries F10, Alt and the mnemonics and the wordmark opens nothing | Mirrors Planboard and Fizz Level Studio. One model also means the shortcut handler uses the same table as the menus |
| D17 | Dialogs and settings | About, Preferences and confirmations are Tauri child windows of the main window (the same page loaded with `?window=<kind>`, under the chrome's title bar with only Close), created by the `open_window` command, centred on the parent and modal for About and confirmations. `src/chrome/dialogWindow.ts` opens one, waits for its answer and closes it, with an in-page fallback for the browser demo only. Preferences is the shared settings shell. The `menuBar` and `theme` settings live in `settings.json` in the app's config directory, read and written by `read_settings` and `write_settings`, and every window hears changes by the `studio://settings-changed` event. The context menu stays in-page | Child windows work better than overlays on a desktop: they can leave the main window, take the platform's modality and follow the window manager. The open-project picker is already the platform's own dialog. A settings file is shared by every window and survives a cleared webview, which browser storage does not |
| D18 | Driving the Studio in dev | `bun run tauri:dev` runs the shell with `tauri.conf.dev.json` (`withGlobalTauri`), and debug builds off Windows register `tauri-plugin-mcp-bridge` with a `dev-automation` capability that names every window, so the Tauri MCP server can drive the running app. A UI test fails if the release config enables the global Tauri, if the bridge is not gated on `debug_assertions` and `not(windows)`, or if a child window is missing from the capability | An agent and a person can screenshot and click the real window, including its child windows, the same way as in Planboard. Gating at compile time, in the dependency table and in a test keeps it from reaching a release build |
| D19 | Studio engine backend | `EngineBackend` in `li-studio` implements `StudioBackend` over `li-engine`, `li-script` and `li-render-tui` and is what the desktop shell runs; `MockBackend` stays for tests and the browser demo. A preview walks the install flow with `cond::eval_bool` so `when` and branches decide which steps and screens appear, and draws each screen with the `tui` renderer as an SVG text dump. A script test loads the source in the sandbox and runs its hooks against a sample page and plan, so a denied capability is a failed test. `check` is the Studio's checks plus the engine's, not the CLI's `DefaultChecker` | The Studio shows what an install does, not an approximation. Reusing the engine's conditions and scripts means a preview and a real run cannot disagree. The CLI's checker lives in a crate that pulls in packaging, so the Studio keeps its own equivalent checks and adds the engine's |
| D20 | Project layouts, built-in actions and targets | Layouts resolve from the target's theme, then its `fallback` chain in the project, then the shared `installer/layouts/`; `fallback = "plain"` names the built-in look. A step's `on_enter` may be `builtin:check-feed` or `builtin:launch-app`. A target is unique by `os-arch:renderer`, so one platform may ship a `canvas` and a `tui` target | The examples and the Studio keep layouts in one shared folder, which avoids copying every layout into every theme, and the engine now agrees with them. Built-ins are carried out by the lifecycle, so the flow runner skips them. Two renderers on one platform are two targets, not a duplicate |
| D21 | Studio preferences | Preferences is a child window with the shared `SettingsShell` (seven sections: General, Appearance, Editor, Preview, Agents, Projects, Advanced). Every change applies at once and is written to `settings.json` as a merge; a refused write restores the value and says why on its row. The file carries a `version`, is validated field by field in Rust and TypeScript, migrates the two-key file, keeps keys it does not know and holds no secret. `tauri-plugin-window-state` remembers the size of the main and Preferences windows; `tauri-plugin-system-appearance` supplies the colour scheme and reduced-motion setting for Follow system. The agent server starts, stops and moves with its settings, its token is shown only on request and replaced from Preferences, and no log line carries it. Open recent is the one submenu in the otherwise flat app menu | A window like the other Liminal HQ apps' keeps every preference in one place and applies it for real. A merge keeps settings from different windows from overwriting each other, and unknown keys survive a downgrade. A token printed at start ends up in logs, and one that cannot be replaced cannot be revoked. A list of up to 20 recent projects does not fit as flat rows, which is the case D16 allows a submenu for |
| D22 | JavaScript tooling | Bun runs the Studio's JavaScript: a root `package.json` with `workspaces`, `packageManager` set to `bun@1.4.4`, one `bun.lock`, `.node-version` for Node 24, and `bun run` in the Tauri `beforeDevCommand` and `beforeBuildCommand`. CI uses `oven-sh/setup-bun`. | The Liminal HQ house patterns choose Bun for new apps; pnpm was a default, not a decision |
| D23 | Rich previews | `run_preview` returns each step's resolved layout tree, page state and sample values, and the Studio draws them as the target's look (DOS text, Windows 95 classic, Afterglow or Neutral) from one HTML renderer that the Layouts screen shares; the `tui` text dump is a collapsible extra for `tui` targets. A theme keeps its own install-flow layouts in `themes/<id>/layouts/`, and `layouts/` holds the plain fallback. Neutral gains a generic `installshield-classic` theme. VT323 is bundled from `@fontsource/vt323` | A text dump does not show what a person sees, and the examples should look like the designs. One renderer for both screens means a layout edit and a dry run cannot disagree. Per-theme layouts stop the DOS and Windows looks sharing one tree with overrides, which the designs differ too much for |
| D24 | Project folder names | The engine loads a project from the folder that holds `installer.toml` (`Project::load_installer_dir`), whatever it is called; `Project::load` still takes the folder that holds `installer/`. The Studio uses the former | The Studio already opened any folder with an `installer.toml`, so check and preview must not refuse the same folder |
| D25 | Headless MCP | `liminst studio --mcp [--port N]` opens the `-C` project over `EngineBackend` and serves `McpServer` on `127.0.0.1` until Ctrl+C. Standard output starts with `Studio MCP server: <url>` and `Token: <token>`, a new token each run, printed once. History is in memory and writes go to disk | CI and remote shells can have an agent edit a project without a window, and the one stdout format lets a script read the address and token. A token in stdout is the only way a headless run can hand it over |
| D26 | GraphQL | Deferred. The Studio's agent API is MCP only | MCP covers what an agent needs, and a second API would double the surface to keep in step before anything uses it. The decision is revisited when a client needs queries MCP tools cannot answer |
| D27 | More Studio windows and menu items | New project (`Ctrl+N`), Keyboard shortcuts (`Ctrl+/`) and Connect an agent are child windows, from the File and Help menus. `liminst init`'s scaffold moves into `li_studio::scaffold` so the Studio and the CLI write the same files. A failed agent server start is kept by the shell and shown on the agent card and in Preferences. Opening a different project resets the per-project state of the app. Build all and the Feeds and Builds screens wait for a later change | The design lists these items, and a form that writes the files itself would drift from `liminst init`. A start failure that only reaches stderr is invisible in a desktop app. Stale ids and selections from another project made the new one load nothing |
| D28 | Script editor | The Scripts screen is CodeMirror 6 mounted by hand and kept alive across redraws, with the packages pinned to the versions Fizz Level Studio uses. The text lives in `scriptDraft` in app state, and `scriptDirty` is derived from it. Syntax errors come from `check_script_syntax`, which compiles the source in an empty Lua state without running it, and the warnings (undeclared capabilities, removed globals, hook parameters, what the retro subset lacks) come from the same call. `test_script` takes a target and builds its sample from it | Unsaved text in a textarea was lost by any redraw and invisible to File > Save. Running a script's top level to find errors would execute it, and a real parser cannot be written twice in the UI. A test that ignores the target cannot show how a script varies across targets. The retro subset list is the one assumption: `li.net`, `utf8`, `string.pack`, `string.unpack`, `string.packsize`, `goto` and `<close>` |
| D29 | Studio identifier and dev port | The bundle identifier is `ca.liminalhq.installerstudio`, the house form with no separators. The settings and window-size files live in the directory named after it, so the first run under it copies `settings.json` and `.window-state.json` from `hq.liminal.installer-studio` once, when the new directory has no settings. Logs are not carried over. The dev server stays on port 1420 with `strictPort`, and a test fails if `devUrl` and Vite differ | The house patterns name `ca.liminalhq.<app>` without separators (Android package names cannot hold hyphens either). Moving the directory would otherwise reset every setting, and the copy is a few lines that a test covers |
| D30 | Typed bindings | ts-rs 12 writes the TypeScript for every Rust type that crosses the Tauri boundary or the MCP API into `packages/protocol/src/generated/`, the private source-only Bun workspace package `@liminal-hq/installer-protocol`. The files are committed, and the `Bindings drift` job regenerates them and fails on a diff. `li-model` and `li-script` derive behind a `ts` feature that `li-studio` enables; `li-studio` derives directly. The UI keeps `lib/types.ts` as a barrel of re-exports. `Settings` and `AppInfo` stay hand-written, held in step by an existing test | The house patterns choose ts-rs with committed, drift-checked bindings. Two copies of a wire type drift, and the UI had a hand-written copy of each. A feature keeps ts-rs out of the runner and the packaged installer. The settings schema carries UI limits and a browser fallback that a generated type cannot express |
| D31 | Structured errors | Every Tauri command returns `Result<T, StudioError>`, and `StudioError` serialises as `{ kind, message }` with kinds `not_found`, `invalid_input`, `io`, `project`, `script`, `backend`, `agent` and `internal`. The MCP server sends the same object in a JSON-RPC error's `data` and in a failed tool's `structuredContent`; a failed tool still returns `isError: true` with the message as text. The UI parses a rejection into a `StudioError` class and shows its `message`. A project that fails to open with `invalid_input` stays in the recent list; other failures drop it | A bare string leaves a caller nothing to branch on but its wording. One shape for the shell and for agents means a script or an agent reacts to `not_found` the same way the UI does. Keeping `isError` on tools is how MCP clients learn a tool failed, and `structuredContent` adds the kind without changing that. A broken project is still there to fix, unlike one that has moved |
| D32 | Prettier and test reports | Prettier (tabs, single quotes, 100 columns, trailing commas) formats the Studio UI's TypeScript, CSS and JSON, and a `Prettier` job checks it; the vendored chrome, the design-token files and generated bindings are ignored. `cargo nextest` has `default` and `ci` profiles in `.config/nextest.toml` (CI retries once, never stops at the first failure, and writes JUnit to `target/nextest/ci/junit.xml`). A `workflow_run` workflow publishes the report as a check run, the Waypoint pattern | The house patterns ask for Prettier with tabs and nextest with a `ci` profile. Vendored files are refreshed by their recipe, and generated files by their generator, so a formatter must leave both alone. Publishing from `workflow_run` is what lets a fork's pull request get a check run, because the `pull_request` token cannot write checks |
| D33 | App layout and the chrome package | The Studio follows the house reference layout: `apps/studio/{index.html,vite.config.ts,src/,src-tauri/}`, with the Vite page in the app folder itself and the shell's `src-tauri` beside `src`. `tauri.conf.json` runs `bun run dev` and `bun run build` and loads `../dist`. The vendored chrome is the workspace package `packages/chrome` (still `@liminal-hq/studio-chrome`, with its `PROVENANCE.md` and refresh steps), imported by deep path (`@liminal-hq/studio-chrome/TitleBar/TitleBar`), with no barrel file | Every app that shares the pattern has one place to look for the page, the shell and the shared packages, and a workspace package resolves like the protocol package does instead of a `link:` into a vendor folder. The chrome keeps its recipe, so it is still refreshed, never edited |
| D34 | React screens, zustand stores and a router | The screens are React 19 components. State is in zustand 5 stores (`src/stores/`: the project and its documents, the dry-run preview, the script draft, the toasts, and the chrome store), with `createStudio` holding the actions, and the backend injected as `api` so a test hands in a fake one (`startApp(root, chrome, { api })` is the seam). The main window's five screens are TanStack Router routes on memory history; child windows are still the same page with `?window=<kind>`, as Planboard does. The CodeMirror editor is a component that mounts one view and syncs the draft and the Editor settings, and is made again when the Scripts screen is shown, with the draft kept in the store (the undo history is not). The dry-run renderer is `src/preview/PreviewTree.tsx` | The chrome was already React, so one framework replaces a hand-built DOM layer and two ways of rendering. Stores keep the draft and the project when a screen goes away, so a redraw cannot lose an edit, and a screen reads only the slice it shows. Memory history keeps the router out of the address bar, which a desktop window does not have |
| D35 | CSS Modules and `--lis-*` tokens | Styles are CSS Modules next to the components, over one global `src/theme/base.css` (elements, focus, density and motion). The design tokens are `--lis-*` custom properties in `src/theme/tokens.css`, generated by `bun run tokens` from the design system export in `src/theme/tokens.json`, followed by `src/theme/chrome-map.css`, which maps every `--lic-*` variable the chrome reads and the editor's syntax colours onto them. The dark, light and system themes are the same `data-theme` blocks as before | The house pattern is CSS Modules with a per-app token prefix, and a module's class names cannot collide with the chrome's or CodeMirror's. One generated file means the design system export stays the only source of colour |
| D36 | Message catalogue | Every visible string is in `src/i18n/messages.ts`, read with `t('area.key')` and `tn('area.key', count)` (typed keys, `{name}` tokens, `.one` and `.other` plurals). `en-CA` is the source. The pseudo-locales `en-XA` (accented and 30% longer, in brackets) and `ar-XB` (right to left) are generated from it and load only in a development build, with `?locale=` in the address. `bun run check:i18n` (also in `make validate` and the `i18n` CI job) fails on a literal in JSX text or a visible attribute, a pseudo-locale that differs from English, a plural without `.other`, and an unused message. Backend messages (flow validation text that mirrors `Flow::validate`, the demo data, and the Lua API reference in `luaDocs.ts`) are not catalogue entries | Strings that are all in one place can be checked, lengthened and mirrored before a translator sees them, which is how the other Liminal HQ apps do it. Text a backend or a reference page owns stays with its source so the two cannot drift |
| D37 | Theme stage and the whole screen | A theme may carry a `stage` layout (`themes/<id>/layouts/stage.layout.json`) with a `slot` node; the page's layout goes in the slot and `show_on` and `hide_on` limit a stage node to steps. `Layout::composed` and `Project::screen_for` compose it for the preview, the runner and `liminst preview`, and the Studio composes the same screen in TypeScript to draw and edit it, with each node tied to the stage or the page. The Layouts screen shows the whole screen, marks stage nodes as shared by every page of the theme, and offers a page its own copy | The backdrop, wordmark, status meters and taskbar were copied into every page of a theme, so they could be neither edited once nor offered on their own, and the Layouts screen drew less than the Dry-run. A page that draws its own `backdrop` keeps working, so existing projects load unchanged |
| D38 | Interactive previews and the full-screen window | The Layouts preview selects the node under a click (every drawn element carries a `data-node-path` of `s:` or `p:` and a path), and the Dry-run preview runs: Next and Back step the flow past skipped steps, controls change the page state, space and the plan follow the choice, and a Play button animates the meters and billboard. Full screen is a child window, `preview` (`?window=preview&target=…&step=…`), opened at the look's natural size scaled to the screen and able to go truly full screen; a browser tab fills the viewport in the page instead. View > Full-screen preview is `F11` on the Dry-run screen | A preview is for judging a design, which needs clicking and a large view; the app's rule that extra views are Tauri windows holds, and a browser tab has no windows to open |
| D39 | The real terminal in the Studio | The Studio shows the `tui` renderer's own output for `tui` and `tui-retro` targets, and lets a person play it. `li-render-tui` returns the ratatui buffer as a `CellGrid` (`render_cells`, with `to_ansi`), `li-studio` keeps live sessions in Rust (Tauri commands and the MCP tools `tui_render` and `tui_key`), and the UI draws the grid on a canvas, with box and block characters drawn as shapes, and forwards keys | An HTML lookalike can drift from what the terminal shows, and the text dump has no colour or interaction. The sessions keep the webview free of terminal state, and the same frames serve agents as text and ANSI. A canvas gives exact colours and gap-free frames whatever fonts are installed. Alternatives were an xterm-style emulator fed ANSI (a dependency and a second parser for what the grid already says) and a DOM grid (box characters seam with font fallback) |
| D40 | DOS runtime in Rust on Desk's foundation | `tui-retro` for `dos-x86` is `SETUP.EXE`, written in Rust: a copy of Desk's `dos/` (target spec, linker script, `rt` crate, go32 packer, DOSBox harness) in `dos/`, its own Cargo workspace with its own lockfile, recorded in `dos/PROVENANCE.md`, over a portable `no_std` core (`li-retro`) that the host tests too. Windows 3.1 stays C with Open Watcom (`retro/`) | Desk had already proved Rust on DOS with no C compiler or library, and a shared core means the flow VM, the renderer and the installer engine are tested on the host. House rules allow copies with provenance, so nothing is fetched at build time but the test tools |
| D41 | No Lua on DOS in v1 | The DOS runtime carries out `builtin:` actions only: `detect-sound` and `check-disk-space` join `check-feed` and `launch-app`. `liminst check` reports a script hook on a `tui-retro` target as `script-on-retro`, and `build` refuses it | A Lua interpreter would cost more memory and floppy space than the rest of the runtime, and the two scripts the example needed are small and fixed. The built-ins are no-ops on the host runners, which skip the steps that name them |
| D42 | The Fizz-DOS artboard is the text look | `li_render_tui::flatten_artboard` draws a `backdrop` layout as the DOS setup screen (title bar, side column with block art and step bar, shadowed dialog, `< Button >` buttons, hint bar) into 80 by 25 cells. The DOS runtime draws widgets over those cells and keeps the focus description out of the grid | One look in the DOS runtime, the CLI and, once it paints the cells, the Studio's terminal view. The flattening lives in li-render-tui so they can share it |
| D43 | `SETUP.DAT` beside `SETUP.EXE`, CRC-32 receipts (the file is `SETUP.LPK` since D51) | The compiled project and payload are one file next to the executable, packed behind CWSDPMI's `CWSDSTUB.EXE` so no DPMI host is needed. The receipt `INSTALL.LIR` records CRC-32, not SHA-256 | A second file keeps the executable one build for every project, and a 386 has no use for SHA-256 on every file. The floppy image holds both files |
| D44 | The terminal in the full-screen window | The full-screen preview window has the same View switch as the Dry-run and Layouts screens for `tui` and `tui-retro` targets, and is opened with the step, target and view on show (`&view=terminal`). The terminal is 80 by 25 cells drawn at the largest whole-number zoom that fits, centred; inside it every key, Esc included, goes to the installer, and F6 leaves it so Esc then leaves full screen and closes the window | A window opened from the real terminal fell back to the rich drawing, so the view the person was judging disappeared. Whole-number zoom keeps cell edges sharp and the aspect fixed; resizing the session to the window would change the DOS look, which is 80 columns, and reopen it on every drag. One rule for Esc (the focused terminal owns it, F6 hands it back) matches the screens, where Tab already belongs to the terminal |
| D45 | A Windows 11 theme for Lieutenant Fizz | `fizz-modern` is a theme stage and page layouts for the `windows-x86_64:web` target, drawn by a fifth Studio look (`win11`) in Fluent's idiom: a Mica window with caption buttons, a step rail, switches, slim rounded progress bars and the status meters as a band above the footer; Fizz's red is the accent and the pixel-art teal the second colour. It is light or dark by the system's scheme, with a Studio switch to pin one. It adds the `variant` (`link`, `hero`) and `control` (`toggle`) properties and no node kinds, and the three modern looks share a `.pvModern` token set. `liminst` takes `os-arch:renderer` to pick between two targets of one platform | The Fizz installers had no Windows 11 look. A stage keeps the wallpaper and the meters in one place; a rail of `step-item` texts per page is how Afterglow already does steps, so no `rail` node was needed, and a prop on `image`, `button` and `checklist` covers the hero, the link and the toggles without a new kind in every renderer. Sharing tokens, not rules, keeps Windows 11 free to differ where Fluent does (8px windows, 4px controls) while reading as kin of Afterglow. The existing `windows-x86_64` id stays on the classic target, so the new target is the second one of that platform and needs a way to be named |
| D46 | `win16` runtime language | Rust `no_std` built for LLVM `code16`, linked by `rust-lld`, rewrapped into a Win16 NE executable by `retro/win16/tools/ne_pack.py`, with Open Watcom C kept as the fallback. The Win16 floor is a 386 or later in 386 Enhanced mode, with no Win32s. Every API stub saves EBX, ESI and EDI, clears the high half of ESP and reloads ES | The spike ran a 14.9 KB Rust installer on Windows 3.11, Windows ME and Wine, and `SETUP` copied a file and wrote an INI receipt. Windows clobbers BX and the high half of ESP, and Standard mode on a 286 is not covered. See [win16-spike.md](win16-spike.md) |
| D47 | The Liminal Pack (`.LPK`) | One pack format for every runtime, in `crates/li-lpk` and specified in [lpk-format.md](lpk-format.md): a 48-byte header and a 32-byte footer on every volume, a directory of variable-length entries (8.3 and long names, size, DOS date and time, attributes, CRC-32, flags `EXECUTABLE`, `REPLACE_IF_NEWER` and `SHARED`, a target mask), and files in chunks of at most 32 KiB that are stored or deflated. Version 1.0 with a major and minor number; a reader accepts any minor of its major and refuses unknown must-understand bits, so a later minor can add fields. It replaces the `SETUP.DAT` layout going forward and is the pack Quill's planned `.QPK` was going to be; Lt. Fizz 2 keeps `.FAP` | One reader to test and ship for DOS, Win16 and Win32, instead of a payload layout per runtime. The container ideas come from `.FAP` and `.QPK`, which Lt. Fizz 2 and Quill designed first |
| D48 | Raw deflate in independent chunks | Each chunk is a raw DEFLATE stream that refers to nothing outside itself, so the decoded-chunk buffer (at most 32 KiB) is the window and a 16-bit unpacker needs no other large buffer. A chunk that does not shrink is stored. The decoder is written in `li-lpk` (input through a 256-byte buffer, output into the caller's window, no `alloc`, no `unsafe`) rather than reusing Fizz 2's, which needs the whole stored section in memory, or `miniz_oxide`, which needs `alloc` and a 32 KiB state of its own. A custom codec was not worth it: LZSS and LZ4 are about 24 % bigger (Fizz 2's measurement) and save about 1 KB of code. Independent chunks cost 7 % on text and 3 % on executables at 32 KiB | Fizz 2's `.FAP` and Quill's `.QPK` proposal both chose raw deflate, and the Quill proposal chose the 32 KiB chunk for Win16, so the two agree; every host has a deflate encoder, so the packer is a small wrapper |
| D49 | `liminst lpk`, not a separate binary | `liminst lpk pack`, `list`, `unpack` and `verify` are a subcommand of the existing CLI, built on `li_lpk::host`, which holds the file and 8.3 name handling so another binary could reuse it.
